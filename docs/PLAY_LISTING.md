## Subscription products — shelved, do not create these

**Nothing is sold in the Android build.** Every converter is free and uncounted, so the paywall is
unreachable and these products must **not** be created in the console: a listing that offers
purchases an installed app cannot make is a listing Play can reject, and a live subscription with no
way to buy it is worse.

The section below is kept, unchanged and unused, for the day selling comes back. Two switches turn
it on, in this order: the Android branch in `createSubscriptionRepo`, which is what stops the store
repository from being built at all, and then the Android tier in `AppQuotaLimits.isMetered`, which is
what stops the counting. Read the section as a specification, not as a task.

<details>
<summary>The two products, if the subscription is ever switched back on</summary>

Create **two** subscriptions. The IDs must match `lib/project_files/features/subscription/domain/store_products.dart`
exactly — one character out and the app sees nothing on sale.

| Field | Monthly | Yearly |
| --- | --- | --- |
| Subscription ID | `archonex_pro_monthly` | `archonex_pro_yearly` |
| Name | Unlimited, monthly | Unlimited, yearly |
| Base plan ID | `monthly-autorenew` | `yearly-autorenew` |
| Billing period | 1 month | 1 year |
| Price (USD) | `0.99` | `7.99` |
| Renewal | Auto-renewing | Auto-renewing |
| Grace period | 7 days | 7 days |
| Free trial | none | none |

**Benefit description**, both plans:

```
Convert as many files as you like, with no monthly count. Every converter, every format, any size.
```

Consider setting lower prices for specific countries under *Set prices by country* — that is the
right lever for affordability, rather than dropping the global price. Play's global floor in USD is
$0.99; a handful of markets allow less.

### The order the console needs them in

The subscription and its base plan are activated **separately**, and only the second one is easy to
miss. An active subscription whose base plan is still inactive is returned by `queryProductDetails`
as nothing at all — the same answer as a product that was never created. Inside the app that becomes
`CatalogProblem.nothingOnSale`, and the paywall drops the Subscribe button and keeps only *Restore
purchases*, which is precisely what a shipped build with an unconfigured console looks like.

1. A payments profile must exist first, under *Monetise with Play*. Without it the price fields are
   refused.
2. Create the subscription. **Subscription ID and base plan ID cannot be changed afterwards** — a
   typo is a dead product in the console for good.
3. Add the base plan, set prices for every country, then **activate the base plan**.
4. **Activate the subscription.**
5. Repeat for the second product.

Nothing has to be rebuilt or re-uploaded for any of this: products are answered from Play's servers,
so an already-published build starts selling within minutes of activation.

### License testers

Play Console → *Setup* → **License testing**, at the developer-account level rather than the app's.
Listed accounts buy without being charged and renew on a compressed schedule. The account has to be
the one signed into the Play Store on the test device, and the app has to have been installed from
Play by that account — a sideloaded copy is not served billing at all.

## Data safety

The app collects and shares nothing, which makes this section short. Answers:

| Question | Answer |
| --- | --- |
| Does your app collect or share any of the required user data types? | **No** |
| Is all of the user data collected by your app encrypted in transit? | n/a — no data is collected |
| Do you provide a way for users to request that their data be deleted? | n/a — no data is collected |

Notes to keep to hand if a reviewer asks:

- Files selected by the user are read and written locally, never transmitted. There is no server.
- Local preferences hold only the interface language. None of it identifies the user, and it is
  removed on uninstall.
- **The app makes no network requests at all.** Nothing is sold, so not even a billing call is made.
  The `INTERNET` permission still arrives through the Play Billing library that the store plugin
  pulls in; nothing in the app uses it.
